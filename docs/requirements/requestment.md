# 要件定義
## 1. 背景・目的
- 要件定義からテストまで、AIを利用して対応する体制をとる。
- 中古自動車販売の整備工場における、部品・消耗品の在庫管理を行うシステムを開発する。現状は紙ベースでの管理と想定し、以下の課題解消を目的に、システムの新規開発を行う。
  - 在庫管理が手作業かつリアルタイムの把握ができない
  - 入庫・出庫管理ができていない
  - 欠品に気が付けない

## 2. システム概要
- システム名称
  - 整備部品在庫管理システム
- 想定ユーザ
  - 整備士(10名程度)
  - 管理者級の整備士を置き、上記10名のうち2名程度とする
  - 権限による操作は、DBの直接編集とする
- 認証方式
  - Google Workspace未契約のため、Session.getActiveUser()による自動識別は採用しない
  - メールアドレス入力 → 許可リストとの照合 → セッション内保持、による簡易ログイン方式を採用する
- ユーザ操作端末
  - 個人所有のスマートフォン
    - QR読み取り、在庫確認
  - 貸与PC
    - QRコード発行と印刷、閾値設定、在庫の手動操作
- 管理対象
  - 部品・消耗品などの在庫
- 開発方針
  - Googleサービスを中心としたローコスト構成をとる
  - DBはGoogleスプレッドシートを軸に検討
  - QRスキャン画面のみ、技術的制約により外部無料ホスティングを併用する(6章参照)
- 出口
  - 検証可能な程度の完成度

## 3. 業務フロー
  1. 利用開始時、メールアドレスを入力し許可リストと照合してログインする(以降のセッション中、入出庫操作時の操作者として記録される)
  2. 在庫アイテムの識別コードには、以下いずれかを用いる(全品目にQRコードを発行・貼付するのは非現実的なため、bを基本としaは補助的に使う)
    a. 自社発行のQRコードを生成・印刷し、棚もしくは部品箱に添付する
    b. メーカーが製品にあらかじめ添付しているバーコード(JANコード、GS1 DataMatrix等)を、そのまま識別コードとして用いる
  3. 整備士は入庫時・出庫時にスマホで上記いずれかのコードを読み取る
  4. 読み取ったコードが在庫マスタに未登録の場合、品目名・閾値・保管場所を入力してその場で新規登録し、登録と同時に読み取った1点を入庫として記録する
  5. 読み取ったコードが登録済みの場合、入出庫の分類と数量を入力し、在庫数の増減を行う(1回の読み取りにつき±1を基本とする)
  6. 在庫数が設定した閾値を下回った(在庫数 <= 閾値)時、担当者宛にアラートメールを自動送信する
    a. アラートメールは、閾値を下回った(在庫数 <= 閾値)1回のみ、補充するまで再送はしない
  7. 在庫一覧画面でいつでも在庫数の確認ができる
  8. 在庫一覧画面でいつでも在庫数の操作ができる

## 4. 機能要件
- FR-01
  - ログイン機能
  - メールアドレスを入力し、許可リストと照合する
  - 一致した場合のみダッシュボードに遷移し、以降の操作者情報として保持する
  - 未登録メールアドレス、または退職フラグがtrueの場合はアクセスを拒否する
- FR-02
  - 在庫一覧表示UI
  - 品目ID、品目、現在在庫数、アラート閾値を一覧表示
  - 管理者級の整備士はデータベースの直接編集が可能
- FR-03
  - QRコード生成機能
  - 品目ID、品目ごとにユニークなQRコードの生成
- FR-04
  - QRコード印刷機能
  - 生成したQRコードをラベル印刷できる形で出力
  - 紙印刷でも可
- FR-05
  - コード読み取り機能(スマホ)
  - スマホのカメラで、自社発行QRコードまたはメーカー添付のバーコード(JANコード/EAN-13、GS1 DataMatrix等)を読み取り、対象品目を特定する
    - ※技術検証(technical_verification.md)の結果、本画面はGAS(HTML Service)ではカメラにアクセスできないため、外部ホスティング上の独立ページとして実装する(6章参照)
    - ※JANコードは13桁の数字自体がGTIN(先頭に0を付与しGTIN-14として正規化)、GS1 DataMatrixはGS1 Application Identifier構造からAI「01」(GTIN)を抽出し、いずれも品目IDとして扱う。実機検証はverification/gs1-datamatrix-scan/にて実施済み
- FR-06
  - 出庫処理
  - 読み取り後、指定数量を在庫数からマイナスする
  - ログイン中のメールアドレスを操作者として入出庫履歴に記録する
- FR-07
  - 入庫処理
  - 読み取り後、指定数量を在庫数にプラスする
  - 入庫後、現在在庫数と閾値を比較して在庫マスターのアラートメール送信済みフラグを更新を判断する
  - ログイン中のメールアドレスを操作者として入出庫履歴に記録する
- FR-08
  - 閾値設定機能
  - 品目ごとにアラート発生の閾値数量を設定
- FR-09
  - 在庫アラートメール自動送信機能
  - 在庫数が閾値を下回った時、通知先設定に登録されているすべてのメールアドレスに自動メール送信
  - メール送信後、在庫マスターのアラートメール送信済みフラグを更新する
- FR-10
  - 入出庫履歴記録
  - ログ保存
- FR-11
  - 廃番品目のチェック
  - 廃番(入手不可能な)品目をデータベース上廃番として管理できるようにする
  - 管理者級の整備士のみ操作可能
- FR-12
  - 未登録品目のスキャン時自動登録機能
  - スマホで読み取ったコードが在庫マスタに未登録の場合、その場で品目名・アラート閾値・保管場所を入力して新規登録できる
  - 登録と同時に、読み取った1点を入庫として記録する(在庫数0のままでの登録は行わない)
  - 新規登録直後は入庫(IN)のみ可能とし、出庫はできない(未登録品目からの出庫は不整合となるため)

## 5. 非機能要件
- NR-01
  - 利用者数
  - 最大アクセス数は最大10名程度
- NR-02
  - 可用性
  - 致命的な業務停止を避ける代替手段を用意
  - 最悪、復旧後に棚卸等行う運用
- NR-03
  - セキュリティ
  - 利用者は整備士に限定
  - Google Workspaceは契約していない前提で、メールアドレス入力+許可リスト照合による簡易ログインでアクセス制御する
  - 本方式はパスワード等を伴わない簡易認証であり、他人のメールアドレスを入力することでなりすましが可能な点は許容リスクとする
- NR-04
  - コスト
  - 原則、Googleの無料枠の範囲で運用する
  - GmailApp送信数の日次上限(個人アカウントの場合100通/日程度)に留意する
- NR-05
  - 保守性
  - 一人開発+AIコード生成を前提に、コードコメント・処理の単純化を重視し、属人化を避ける設計とする
- NR-06
  - 拡張性
  - 将来的な品目数増加、拠点追加、他システム連携を見据えた最低限の拡張余地を残す

## 6. システム構成
- アーキテクチャ
  - レイヤード構成(API層、ロジック層、データアクセス層)を採用する
- データベース
  - Googleスプレッドシート(在庫マスタ、入出庫履歴、通知先設定、許可リストをシート管理)
- バックエンド
  - Google Apps Script
    - ログイン機能:入力メールアドレスを許可リスト(7.4)と照合し、CacheServiceにセッショントークンを保持する(技術検証済み。トークンをクライアント側JS変数に保持し、以後の呼び出しに付与する方式)
    - 閾値判定ロジック
    - Gmail送信は GmailApp.sendEmail()
    - 出庫の時、在庫マスターのアラート送信済みフラグがfalseであればアラートメールを送信する
    - LockService(LockService.getScriptLock())による排他制御を行い、同時書き込み競合対策をする
      - 許可リスト照合ロジックをGAS側で実装する
      - 管理者の整備士に対しては、Googleスプレッドシートの編集用UIを表示する
      - 技術検証で判明した注意点:スプレッドシート書き込み後、ロックを解放する前にSpreadsheetApp.flush()を呼び出し、変更を確定させること(呼び出し漏れがあると排他制御が形骸化する)
    - 許可リスト照合ロジックをGAS側で実装する
    - 管理者の整備士に対しては、Googleスプレッドシートの編集用UIを表示する
    - GF-03(外部ホスティング)からの呼び出しに対応するため、doPostをJSON API化する
      - CORSプリフライトを回避するため、リクエストのContent-Typeはtext/plain;charset=utf-8とし、GAS側でJSON.parse(e.postData.contents)により本文を解釈する
      - application/jsonを指定するとGAS側がpreflightのOPTIONSに応答できず失敗することを検証で確認済み
- フロントエンド
  - GF-00、GF-01、GF-02、GF-04、GF-05
    - Google Apps Script(HTML Service)
  - GF-03
    - 独立したHTML/JS(外部ホスティング上に配置)
- コード読み取り
  - スマホブラウザの「getUserMedia」+ ZXing-js(マルチフォーマット対応。QR/JAN(EAN-13)/GS1 DataMatrix等を1画面で読み取る)
  - 実装方式・カメラアクセスの動作は技術検証用サンプル(qr-scan-verification.html、verification/gs1-datamatrix-scan/)で確認済み
- QRコード生成・印刷
  - JS製QRコード生成ライブラリを利用した内製

### 6.2. 技術検証結果を受けた全体構成方針
- 技術検証の結果、QRコード読み取り(カメラアクセス)がGoogle Apps Script の HTML Service では実現不可能であることが判明した(Google公式トラブルシューティングドキュメントで、HTML Serviceのサンドボックス環境がカメラ・マイク等の機微な権限を要するWeb APIを制限すると明記されており、Google自身が「別ドメインでホストする」ことを回避策として案内している)。
- これを受け、システムを以下の2系統に分割する構成に変更する。
  - GF-00、GF-01、GF-02、GF-04、GF-05
    - Google Apps Script(HTML Service) にホスティング
      - カメラ機能不要のため制約なし
  - GF-03
    - 外部無料ホスティング(GitHub Pages 等の静的ホスティング)
      - カメラアクセスにはGASのiframeサンドボックス外への切り出しが必須
    - GF-03からGASへは、スプレッドシート(DB)への読み書きAPIとしてdoPost/doGetをfetch()で呼び出す構成とする

## 10. リスクとその対応方針
- 通信失敗
  - プログラム的にリトライを行う
- 退職・異動時のアクセス権限失効漏れ
  - 許可リストの定期棚卸を行う
- なりすましリスク
  - 検証レベルの運用として許容する
- 管理者のDB直接編集とLockServiceの競合リスク
  - 管理者のスプレッドシート直接編集は、GAS側のLockServiceによる排他制御の対象外である
  - 対応:整備作業中(整備士がQRスキャンで入出庫操作を行っている時間帯)は直接編集を行わない運用ルールとし、技術的な排他制御は行わない。万一競合が発生した場合は、定期棚卸(NR-02と同様の運用)で在庫数を実数に合わせて解消する
- GASのカメラアクセス制限による構成分割リスク(技術検証で新たに判明)
  - GF-03のみ外部ホスティングに分離したことで、システムが2ドメインにまたがる構成となり、単一のGASプロジェクトで完結する場合に比べて保守対象が増える(NR-05属人化回避の方針との緊張関係)
  - 対応: GF-03側のコードは最小限(スキャン・API呼び出しのみ)に留め、業務ロジックは全てGAS側に集約する
- GAS⇔外部ホスティング間のセッション連携リスク
  - ログインセッション(トークン)をGAS(HTML Service)から外部ホスティング(GF-03)へ引き継ぐ必要があり、URLパラメータ等での受け渡し時に漏えい・改ざんの余地がある
  - 対応:トークンの有効期限を短く設定(例:30分)し、使用のたびに検証する
- 外部ホスティングサービス自体の仕様変更・停止リスク
  - GitHub Pages等の無料サービスの仕様変更や停止により、QRスキャン画面が利用できなくなる可能性がある
  - 対応: NR-02(可用性)の代替手段として、緊急時は紙による入出庫記録に切り替え、後日まとめてシステムに反映する運用を明文化しておく
- Googleの仕様変更による再発リスク
  - 今回のカメラアクセス制限は2026年前後に生じた比較的新しい制約であり、Google側の今後の仕様変更(改善・悪化どちらも)によって前提が変わる可能性がある
  - 対応: 実装直前(4章 全体設計フェーズ)に本制約の最新状況を再確認する
- 識別コード形式追加(JAN/GS1 DataMatrix)によるコード解析リスク
  - GS1 DataMatrixはApplication Identifier構造の解析が必要で、対応する識別子(AI)を網羅していない場合、GTINを正しく抽出できない可能性がある
  - 対応: 主要なAI(GTIN=01等)のみに対応する簡易パーサとし、未対応AIや解析失敗時はエラーとして扱い、誤った値をitemIdとして登録しない設計とする。実機での読み取り検証はverification/gs1-datamatrix-scan/で継続する

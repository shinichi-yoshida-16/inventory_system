# 技術検証

## 検証結果1
- 最重要項目(QRコード読み取り機能)に致命的な設計変更が必要
  - GAS(HTML Service)ではスマホカメラにアクセスできない
    - Google公式ドキュメント(トラブルシューティングページ、2026年7月更新)に、原因となりそうなの記載を確認
  - 原因
    - ブラウザ側の仕様(Permissions Policy)によるもので、GASのWebアプリはGoogle管理下のクロスオリジンifram内に埋め込まれるため、開発者側ではallow="camera"属性を追加できず、修正不可能
    - つまりGF-03(QRスキャン画面)を丸ごとGASのHTML Serviceで作る計画は、現状では実現できない
  - 対応方針
    - Google公式の推奨に準拠
      - Google自身も「これらの権限を必要とする機能は、Apps Script外の別ドメインでホストし、そちらを開くようにする」ことを回避策として明記している。
      - 無料枠で構成するなら、GitHub Pages(完全無料・静的ホスティング)にQRスキャン画面だけを切り出し、そこからGASをバックエンドAPIとして呼び出す構成が現実的
      - GASのiframeサンドボックスさえ回避すれば、QR読み取り機能は問題なく実装可能

## 検証結果2
- 排他制御(LockService)
  - スプレッドシートを扱う場合、ロックを解放する前に SpreadsheetApp.flush() を呼び出し、保留中の変更をスプレッドシートに確定させる必要がある
  - 呼び出しを忘れると、排他制御が形式的には機能していても、実際の書き込みタイミングがロック解放後にずれ込み、競合が再発するリスク

## 検証結果3
- 簡易ログイン
  - GAS標準のCacheServiceを使ったセッション管理は実例が確認できる、実績のあるパターン
  - GASのHTML Serviceはiframe構成のためCookieでのセッション保持がしにくく、セッショントークンをクライアント側JS変数に保持し、以降のgoogle.script.run呼び出しに毎回付与する方式が定石

## 検証結果4(2026-08-20追記)
- GF-03(QRスキャン画面、外部ホスティング)を、LINE等のアプリ内ブラウザ(メッセージアプリ内蔵のWebView)で開いた場合、カメラが起動できない事象を確認
  - 原因
    - 検証結果1のGAS iframeサンドボックス制約とは別要因。GF-03自体は既に外部ホスティングへ切り出し済みのため、GAS側の制約は受けない
    - LINE/Instagram/Facebook等のアプリ内ブラウザは、独自のWebViewにカメラAPI(getUserMedia)への制限をかけている場合があり、開発者側では制御・回避不可能
  - 対応方針
    - コードでの自動回避(User-Agent判定による外部ブラウザ誘導、手入力フォールバック)は見送り、「QRスキャン画面は必ずSafari/Chrome等の通常のWebブラウザで開く」運用ルールで対応する(全体設計書.md 8.1節、取扱説明書 参照)

## 補足
- GmailApp送信数
  - MailAppとGmailAppはメール受信者数の上限を共有しており、個人アカウントでは1日100受信者まで、Workspaceでは1日1,500受信者(ドメイン内のみなら2,000)。10名規模の運用なら問題にならない、NR-04に明記しておくと安全
- スクリプト実行時間
  - 無料アカウントでの1回あたりのスクリプト実行は6分でハードストップ
  - 今回の処理内容(1件ずつの在庫更新)であれば全く問題にならない水準
